`ladder/rungs/r0.py` — **not written**. `ladder/rung0_ab.py` and `ladder/stub_llm.py` have landed.

## Role

- The only rung that **receives an empty record list**. It is handed `sources` — `{doc_id: text}` — and builds the records every other rung routes.
- One call per document, JSON out, temperature 0.
- Everything above it measures the reliability layers wrapped around this call.

## What it must produce

From the raw post string alone, for every mention:

- **that a mention exists** — that `cramping` is a reaction and `1st pill` is not
- **character offsets** — exact, or [[r1]] fires `span_ungrounded`
- **a SNOMED code**
- `entity_type` — `reaction` or `drug`

## Hard input boundary

- Rung 0 receives `sources`. **Never `docs`.**
- `docs` carries gold spans, gold codes and annotator entity types. A rung 0 that reads them makes rung 1's span check vacuous and its 1.000 span-shift detection an artefact.
- `run.py` passes only `sources`, but nothing enforces it — the constraint is on the implementer.

## Modes: recall vs search

One implementation, one flag. Two implementations would confound tool access with prompting.

| Mode | Behaviour |
|---|---|
| A · `recall` | the model emits a code from memory, no tools. **Manifest default.** |
| B · `search` | the model gets a vocabulary lookup tool |

- `recall` is what "bare LLM" means, and it is what makes rung 1's rejection rate meaningful.
- The A/B is a declared ablation: *does a lookup tool remove errors, or just move them into `overrode_tool`?*

```bash
python -m ladder.rung0_ab --compare
```

## stub_llm.py

The model client `rung0_ab.py` runs against. Ollama.

- Two functions only: `stub(prompt, text, mode) -> (raw, usage)` and `load_items(splits_dir)`.
- **Must not repair model output.** No stripping code fences, no extracting the first `{...}`, no retry on malformed JSON. A parse failure is rung 0's counter-metric; quietly fixing them deletes the measurement.
- The one exception, not a repair: unwrapping Ollama's `/api/generate` transport envelope. Everything inside `.response` passes through untouched.
- `usage` carries real `prompt_eval_count` / `eval_count`, not estimates. Latency recorded per call so p95 is taken over the run.

## Offset recovery

- Landed as a **flag**, so both arms stay measurable — a model that names the right span but miscounts characters is a different failure from one that invents the mention.

## Measured — the A/B on dev

40 dev documents, `granite4:micro-h`, greedy. Offsets recovered by search in both arms so span grounding does not mask the code check. Reactions only.

| | A — recall only | B — tool prompt |
|---|---|---|
| mentions emitted | 176 | 159 |
| rejected by [[r1]] | 176 (100 %) | 92 (58 %) |
| accept / band | 0 / 0 | 0 / 67 |
| **code correct** | **0 / 107** | **0 / 96** |
| null codes emitted | 0 | 59 |
| span precision / recall | 0.679 / 0.459 | 0.645 / 0.410 |
| tokens | 19,701 | 20,431 |
| wall clock | 276 s | 2,410 s |
| overrode its own lookup | — | 29 / 29 |

### The rejection rate is not the result

- B's rejection rate halves. Its **code accuracy does not move** — zero in both arms across 203 graded mentions.
- The entire difference is **59 null codes**. B declines a third of the time, and a record with no code cannot be rejected for a bad one, so it lands in BAND. Those 67 BAND records are abstentions, not successes.
- **The tool prompt bought abstention, not accuracy**, at 8.7× the latency and slightly worse span recall.
- Reading the rejection rate alone would have reported tool access as a 42-point improvement. This is exactly the failure `--compare` exists to catch: the errors moved rather than disappeared.

### The tool was never called

- `honoured_tool` is never `True` — 130 `None`, 29 `False`.
- `vocab.search` runs **after** generation, so the tool block is prompt text and nothing more.
- Where a search did return candidates, the model overrode its own lookup **29 times out of 29**.
- So the contrast measures **prompt wording, not tool access**. Either build a real tool loop or rename the ablation. **Do not publish the current framing.**

### The model cannot code, in either arm

- 0 correct out of 203 graded mentions. Not poor — categorically incapable.
- It locates reactions at F1 0.548 and never once produces the right SNOMED code.
- 164 of 176 codes in mode A **do not exist at all**, so it cannot be right by accident.
- **Extraction and normalisation are different capabilities.** A single accuracy number over both would report half the task working as one middling score, and hide that the half a vocabulary lookup solves is at zero.
- Scope: one model, one size, 40 dev documents, greedy. This says nothing about what LLMs can do; it says what the harness can now distinguish.

## Nothing writes `out/r0.jsonl`

- `rung0_ab.run()` builds `list[Record]` from a real model and `compare()` prints a table — the records stay **in memory**.
- A working model→Record path and a working Record→ladder path exist, and nothing joins them. Either write `ladder/rungs/r0.py`, or add a wrapper that serialises `rung0_ab.run()` output.
