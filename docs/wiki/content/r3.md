Specified below so it can be built without re-deriving the contract. See [[contributing]].

## Trigger

- Fires **only** on `record.checks["r1_verdict"] == "REJECT"`.
- Every other record passes through untouched, and must still get a ledger row (`outcome="unchanged"`, zero cost).
- It **cannot** fix a record that passed validation — there is no fact to feed back. A rung 3 that retries BAND records is measuring prompt suggestibility, not correction.

## The rule

- State `checks["r1_reason"]` **as a fact**: `"code 999999 does not exist"`.
- **Never as a question**: `"are you sure?"`.
- **One** bounded retry. Not a loop.

| `r1_reason` | Fact to state |
|---|---|
| `code_unknown` | the code is in no release of the vocabulary |
| `span_ungrounded` | the quoted text is not at those offsets |
| `span_out_of_range` | the offsets fall outside the document |
| `wrong_semantic_type` | the code is not a clinical finding |
| `code_inactive` | the code was retired (only reachable if `reject_inactive=true`) |

## Input boundary

- May read `checks["r1_verdict"]` and `checks["r1_reason"]`. **Nothing else from `checks`.**
- `checks["meddra_term"]` is derived from the answer key. Putting it in a prompt leaks the answer and invalidates every number above.
- Gets the post text from `sources[doc_id]`, never from `docs`.

## What to write

- On a successful correction: `rec.mark(3, ZONE_BAND)` or re-run nothing — **rung 3 does not re-validate.** Update `rec.sct` / `rec.spans` and let the ladder continue; rung 1 already ran.
- Record the before value so the correction is auditable, e.g. `checks["r3_original_sct"]`.
- On failure to correct, leave the record as it was.

## Ledger

One row per record, `rung=3`:

- `tokens_in`, `tokens_out`, `api_calls=1` — real counts from the client, not estimates.
- `latency_ms` per call, so p95 is taken over the run.
- `outcome="corrected"` or `"unchanged"`.
- Cost is divided by records that **entered** the rung, so a cheap rung 3 shows as cheap. See [[ledger]].

## How you will know it works

- On the gold control it should fire **zero times** — [[r1]] rejects nothing on gold, so a non-zero count means something upstream changed.
- On a prediction file with planted corruptions, it should fire exactly as often as rung 1 rejected.
- The measurement that matters is **marginal**: errors prevented per extra call, from [[ledger]]. Run it alone with `run ablate` to keep the number attributable.

## Open questions

- Does a corrected record get re-validated by rung 1? Currently no rung re-runs another. If it should, that is a `rung_order` change, not a rung 3 change.
- Temperature: `manifest.model.temperature` is 0. A correction retry at 0 may reproduce the same wrong answer.
