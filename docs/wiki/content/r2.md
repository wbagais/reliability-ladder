# Rung 2 · self-correction {{status|BUILT — measured 2026-08-23}}

`ladder/rungs/r2.py` — written. **+1 call per fired record.**

Measured on the dev split (40 docs, granite4:micro-h, GPU): **158 rejections
offered, 0 rescued, 158 declined, 72,539 tokens.** Code accuracy 0/105 before
and 0/105 after. See [[measurement]] and `runs/full-A-*.json`.

## Trigger

- Fires **only** on `record.checks["r1_verdict"] == "REJECT"`.
- Every other record passes through untouched and still gets a ledger row
  (`outcome="unchanged"`, zero cost), so "rung 2 did not fire" is
  distinguishable from "rung 2 was never run".
- It **cannot** fix a record that passed validation — there is no fact to feed
  back. A rung 2 that retries BAND records is measuring prompt suggestibility,
  not correction.

## The rule

- State `checks["r1_reason"]` **as a fact**: `"code 999999 does not exist"`.
- **Never as a question**: `"are you sure?"`.
- **One** bounded retry. Not a loop.

| `r1_reason` | Fact to state |
|---|---|
| `code_unknown` | the code is in no release of the vocabulary |
| `span_ungrounded` | the quoted text is not at those offsets |
| `span_out_of_range` | the offsets fall outside the document |
| `wrong_semantic_type` | the code is not a clinical finding |
| `code_inactive` | the code was retired (only reachable if `reject_inactive=true`) |

## Input boundary — enforced, not observed

- May read `checks["r1_verdict"]` and `checks["r1_reason"]`. **Nothing else
  from `checks`.**
- `checks["meddra_term"]` is derived from the answer key. Putting it in a prompt
  leaks the answer and invalidates every number above.
- Gets the post text from `sources[doc_id]`, never from `docs`.

This is the one rule in the spec whose violation would be **silent** — a leaked
prompt produces better numbers, not an error — so it is enforced in code.
`ALLOWED_CHECK_KEYS` and `_CheckView` raise on any other key rather than
trusting the rung to behave.

## Outcomes

Five, counted separately because they mean different things:

| outcome | meaning |
|---|---|
| `rescued` | changed, and rung 1 now accepts or bands it. The only win. |
| `still_failing` | changed, still rejected. Cost paid, nothing bought. |
| `reasserted` | the model returned the same code. Cost paid, nothing moved. |
| `declined` | the model returned null — no replacement offered. |
| `unchanged` | did not fire. Not a correctable rung 1 rejection. |

`declined` was not in the original spec, and is what actually happens: **158 of
158**. Told a code does not exist, the model never proposes another.

**Rung 2 has no authority to withdraw an answer.** A declined record is left
exactly as it was, still carrying its code and still rejected, with
`checks["r2_declined"]` set for rung 5 to act on. [[r5]] owns abstention, and a
rung 2 that nulls codes duplicates rung 5's mechanism at the wrong rung —
constraint 5 says a withdrawal preserves the original.

Folding `declined` into `rescued` would make rung 1's rejection rate collapse
and report a coverage loss as a reliability gain. The same confound appears at
rung 0 mode B, where the rejection rate halved purely through null codes with
code accuracy unchanged at zero.

## What to write

- `checks["r2"]` holds `outcome`, `reason`, and the full before/after
  (`was` / `now`), so every correction is auditable.
- On a rescue, adopt the candidate's `text` / `spans` / `sct` / `confidence`,
  refresh `checks["r1_verdict"]` and `checks["r1_reason"]`, and
  `rec.mark(3, verdict, reason)`.
- On any other outcome, leave the record as it was.

### Rung 2 DOES re-validate — changed from the original spec

The original spec said rung 2 does not re-validate: update the record and let
the ladder continue. That makes `rescued` an **assertion** rather than a
measurement — the record would be marked BAND because a correction was
attempted, not because it worked.

This spec's own success criterion is *errors prevented per extra call*, and that
cannot be counted without checking whether the new answer is valid. On the
measured run a non-validating rung 2 would have reported 158 corrections, none
of them checked, all of them empty.

`r1.zone()` is a pure function and rung 2 calls **that one measured
implementation**, never a copy. This is rung 2 checking its own output before
claiming a repair, not re-running rung 1 as a rung, so `rung_order` is
unaffected.

## Ledger

One row per record, `rung=3`:

- `tokens_in`, `tokens_out`, `api_calls=1` — real counts from the client.
- `latency_ms` per call, so p95 is taken over the run.
- `outcome` — one of the five above.
- Cost is divided by records that **entered** the rung. See [[ledger]].

## How you will know it works

- On the gold control it should fire **zero times** — [[r1]] rejects 12 of 9,111
  gold mentions, so a large count means something upstream changed.
- On a prediction file with planted corruptions, it should fire exactly as often
  as rung 1 rejected.
- The measurement that matters is **marginal**: errors prevented per extra call,
  from [[ledger]]. Run it alone with `run ablate` to keep the number
  attributable.

## Resolved

- **Does a corrected record get re-validated?** Yes. See above.
- **Temperature 0 may reproduce the same wrong answer.** Measured: it does not.
  `reasserted` was 0 across 158 attempts. The model declines rather than
  repeating itself, which is a stronger signal than repetition would have been —
  it suggests the model can tell its codes are unreliable without being able to
  produce better ones.

## Open

- Rung 2 recovered nothing on a model with no vocabulary knowledge, which is the
  expected result and not a general one. Whether self-correction helps a model
  that *does* know SNOMED is untested and needs a second model.
- Cost is currently aggregated per run, not per record, so the ledger cannot yet
  divide by records entering the rung.
